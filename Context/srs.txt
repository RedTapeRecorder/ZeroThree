# **1. Introduction**
 
## **1.1 Purpose**
 
This Software Requirements Specification (SRS) defines the complete, testable requirements for the LPG Delivery Route Management System, referred to throughout this document as ZeroThree. Every requirement stated here traces directly to a problem or goal documented in ZeroThree BRD v2.1.
 
This document is the authoritative reference for development, testing, and acceptance of version 1 of the system. Any feature not listed in this document is out of scope for v1.
 
## **1.2 Scope**
 
ZeroThree consists of three components built and deployed together:
 
- A rider mobile application for Android
 
- A backend API server
 
- A web-based administration panel for the branch manager
 
The system serves an LPG distribution branch in San Juan City, Metro Manila, covering 7 areas and a network of approximately 550 recorded outlets, of which 50 to 100 are confirmed active.
 
## **1.3 Definitions**
 
| **Term** | **Definition** |
| --- | --- |
| Outlet | A sari-sari store or small retail business that purchases LPG canisters from the branch for resale |
| Rider | A branch employee who travels by motorcycle to deliver and collect LPG canisters |
| Visit | Any recorded interaction between a rider and an outlet, regardless of whether a delivery occurred |
| Shift | A single working day for a rider, beginning at shift-start sync and ending at logout |
| Geofence | A configurable virtual boundary around an outlet's GPS coordinates used to detect rider proximity |
| Active outlet | An outlet currently being serviced, visible to riders on the map |
| Inactive outlet | A known outlet not currently being serviced; hidden from riders but visible to the manager |
| Pullout outlet | An outlet where the LPG product has been physically removed; hidden from riders, visible to manager |
| FCM | Firebase Cloud Messaging — Google's free push notification delivery service |
| Session key | A server-issued encryption key valid for one shift, used to encrypt outlet data on the rider's device |
| Shift-start sync | The process of downloading encrypted outlet data, route, and map tiles to the rider's device at the start of a shift over WiFi |
| Pin quality | A field recording how reliable the stored GPS coordinates are for a given outlet |
| Verification level | A field recording who can confirm the accuracy of an outlet's location and current status |

## **1.5 Requirement notation**
 
**REQ-XXX: **The system shall [action].    [BRD §X.X] [Priority]
 
Requirements use the word shall to indicate a mandatory condition. The word should indicates a strong preference that may be relaxed with documented justification. The word may indicates an optional behaviour.
 
# **2. System Overview**
 
ZeroThree is an offline-first field operations system. The rider mobile app is the primary surface — it must function without internet connectivity for all core delivery logging tasks. The backend API and web admin panel require internet connectivity to operate.
 
The system is designed for a small operation of 1 to 3 riders and must not require structural changes to support up to 10 riders in the future. All outlet data transmitted to rider devices is encrypted with a server-issued session key and wiped automatically at shift end.
 
# **3. User Requirements**
 
## **3.1 Rider — mobile app**
 
**REQ-001: **The system shall allow a rider to view all active outlets with reliable coordinates as pins on a map covering the full 7-area service zone from their first day of use.    [BRD §P1, §5.1] [P1]
 
**REQ-002: **The system shall display the map and all active outlet pins without an internet connection, using data downloaded at shift-start sync.    [BRD §14.1, §15] [P1]
 
*Rationale: Offline map capability is the single most critical feature for new rider onboarding in areas with poor signal.*
 
**REQ-003: **The system shall show the rider which nearby active outlets have gone the longest without a visit, enabling experienced riders to prioritise unserviced accounts.    [BRD §P3] [P3]
 
**REQ-004: **The system shall require a rider to complete a one-time setup using a manager-provided code before the app is usable.    [BRD §6.2] [S]
 
**REQ-005: **The system shall store the rider's authentication token permanently on the device after the first login so that no subsequent login is required under normal circumstances.    [BRD §6.2, §5.1] [S]
 
**REQ-006: **The system shall display a data collection disclosure screen on first login. The rider must tap an acknowledgement button before the app becomes usable.    [BRD §13, §14.1] [S]
 
*Rationale: Required for RA 10173 compliance.*
 
**REQ-007: **The system shall hide all inactive and pullout outlets completely from the rider's map view.    [BRD §7, §5.1] [S]
 
**REQ-008: **The system shall allow a rider to tap any active outlet pin to open its detail screen before checking in.    [BRD §8] [P1]
 
**REQ-009: **The detail screen shall always display: the outlet photo (or a placeholder if none exists), the outlet name and address, the date of the last visit, and the outcome of the last visit.    [BRD §8] [P1]
 
**REQ-010: **The detail screen shall conditionally display the name of the rider who made the last visit, only if the manager has enabled the show_last_visitor flag for that outlet.    [BRD §8] [S]
 
**REQ-011: **The detail screen shall conditionally display the exact time of the last visit, only if the manager has enabled the show_last_visit_time flag for that outlet.    [BRD §8] [S]
 
**REQ-012: **The system shall fetch the outlet photo only when the rider opens that outlet's detail screen. Photos shall not be included in the shift-start sync payload.    [BRD §9] [S]
 
*Rationale: Lazy loading is essential to the under-5MB-per-day data constraint.*
 
## **3.2 Rider — visit logging**
 
**REQ-013: **The system shall automatically detect when a rider enters the geofence radius of an active outlet using GPS polled at a configurable interval, defaulting to 10 seconds.    [BRD §11.1] [P1]
 
**REQ-014: **When a rider remains within the geofence radius for more than 60 seconds, the system shall prompt the rider to log a visit outcome.    [BRD §11.1] [P1]
 
**REQ-015: **When a rider passes through the geofence radius for fewer than 60 seconds, the system shall automatically record a no_stop outcome with no rider input required.    [BRD §10, §11.1] [P1]
 
**REQ-016: **The system shall support the following visit outcome codes: delivered, no_stock, no_stop.    [BRD §10] [P1]
 
**REQ-017: **For a delivered outcome, the system shall capture the following fields separately: number of canisters refilled (at ₱32 per unit), number of new canisters sold (at ₱70 per unit), and total payment collected as a single combined figure. Both unit fields shall accept zero, allowing a visit to record only refills, only new can sales, or both.    [BRD §10, §1] [P1]
 
*Rationale: The branch conducts two transaction types. Refills account for approximately 70% of delivered visits — empty cans exchanged for full ones at ₱32. New can sales account for approximately 30% — a brand new canister sold at ₱70. Both may occur in the same visit and must be tracked separately to enable future outlet segmentation analytics.*
 
**REQ-017a: **The system shall validate that at least one of the two unit fields — canisters refilled or new canisters sold — is greater than zero before a delivered outcome can be saved. A delivered visit recording zero units of both types is invalid and shall not be accepted.    [BRD §10] [P1]
 
*Rationale: Enforced at both app level and database level as a check constraint. Prevents data entry errors where a rider selects delivered but forgets to enter units.*
 
**REQ-018: **The system shall allow a rider to add an optional free-text note to any visit of any outcome.    [BRD §10] [P2]
 
**REQ-019: **The system shall record arrival time when the rider enters the geofence radius.    [BRD §11.2] [S]
 
**REQ-020: **The system shall record departure time when the rider exits the geofence radius.    [BRD §11.2] [S]
 
**REQ-021: **The system shall automatically calculate and store visit duration in minutes from arrival and departure timestamps.    [BRD §11.2] [S]
 
**REQ-022: **All visit timestamps shall be recorded in Philippine Standard Time (PST, UTC+8).    [BRD §11.2] [S]
 
**REQ-023: **The system shall store the GPS accuracy reading in meters at the time of geofence entry with every visit record.    [BRD §11.1] [S]
 
*Rationale: Provides audit evidence for disputed visits and helps identify outlets with problematic GPS conditions.*
 
**REQ-024: **The system shall display a warning to the rider if their GPS position at check-in is outside the geofence radius, but shall allow them to proceed regardless.    [BRD §11.1] [S]
 
**REQ-025: **The system shall queue visit records locally on the device when no internet connection is available and sync them to the server automatically when connectivity is restored.    [BRD §14.1, §15] [P1]
 
## **3.3 Rider — photos**
 
**REQ-026: **After completing any visit of any outcome, the system shall allow a rider to optionally submit a new photo of the outlet.    [BRD §9] [P2]
 
**REQ-027: **A rider-submitted photo shall be held in a pending state on the server. The existing approved photo shall continue to be shown to all riders until the manager approves the submission.    [BRD §9] [S]
 
**REQ-028: **The rider shall receive no in-app feedback when a photo submission is sent. The submission is silent from the rider's perspective.    [BRD §9] [S]
 
## **3.4 Rider — routes**
 
**REQ-029: **When a manager has assigned a route to a rider, the system shall display the route's outlets in the suggested sequence on the rider's map.    [BRD §12] [P3]
 
**REQ-030: **The system shall visually distinguish high priority outlets within a route using a distinct marker on the map pin, different from standard outlet pins.    [BRD §12, §S7] [S]
 
**REQ-031: **The rider shall be able to deviate from the suggested route sequence at any time without restriction.    [BRD §12] [P2]
 
*Rationale: A rider carries approximately 4 × 33 canisters per load. With each outlet taking 5 to 10 or more canisters, a rider exhausts their supply after a small number of stops and must return to the branch to reload before continuing. The actual daily visit sequence is dictated by load cycles and reload availability, not a fixed plan. Route deviation is a physical necessity, not just a preference.*
 
**REQ-032: **The active route shall be included in the shift-start sync payload and stored in encrypted temporary storage on the device, available offline.    [BRD §12, §15] [P1]
 
## **3.5 Rider — data security**
 
**REQ-033: **All outlet data stored on the rider's device shall be encrypted using a session key issued by the server at shift start.    [BRD §13, §14.1] [S]
 
**REQ-034: **The session key shall be revoked by the server at logout or account lock, rendering any cached outlet data on the device unreadable.    [BRD §6.3, §13] [S]
 
**REQ-035: **All outlet data shall be wiped from the rider's device at shift end or logout.    [BRD §13, §14.1] [S]
 
**REQ-036: **The app shall check account status with the server on every reconnect after being offline. A locked account shall display a locked screen immediately upon reconnect.    [BRD §6.3, §14.1] [S]
 
**REQ-037: **Outlet photos shall never be stored permanently on the rider's device.    [BRD §9] [S]

# **7. External Interface Requirements**
 
## **7.1 Firebase Cloud Messaging (FCM)**
 
The backend API shall integrate with Firebase Cloud Messaging to deliver push notifications to rider devices. Each rider account shall store an FCM device token updated automatically by the app on each launch.
 
## **7.2 Cloudinary**
 
All outlet photos shall be stored in Cloudinary. The system shall use Cloudinary's automatic image transformation to compress photos to approximately 200KB on upload. The database shall store the Cloudinary URL and Cloudinary public ID for each photo — the public ID is required for deletion when photos are rejected or replaced.
 
## **7.3 Map tiles**
 
Offline map tiles for the 7-area service zone shall be packaged in MBTiles format and downloaded to the rider device once over branch WiFi. The flutter_map library with MBTiles support shall be used for tile rendering. No live tile fetching shall occur during a shift.
 
## **7.4 Navigation deep link**
 
When a rider taps the navigate button on an outlet detail screen, the app shall open the device's installed navigation app (Google Maps or Waze) via a deep link pre-populated with the outlet's GPS coordinates. The system shall not implement its own turn-by-turn navigation.

# **10. Future Compatibility Requirements**
 
## **10.1 Order intake — background**
 
Outlets currently contact the branch to place orders via phone calls, SMS, Viber, and WhatsApp. The manager receives these through multiple channels with no consistent recording system, then relays them verbally to riders by phone. There is no link between an inbound order request and a fulfilled delivery.
 
Version 2 will introduce a formal order intake screen in the web admin where the manager logs inbound orders as structured records, assigns them to riders, and tracks fulfillment. The v1 database schema is designed to support this without structural changes.
 
**REQ-101: **The visits table shall include a nullable order_id field (UUID type) from initial deployment. This field shall not be exposed in the v1 rider app or web admin interface but shall be present in the database schema to support order-to-fulfillment linking in v2 without a destructive schema migration.    [BRD §G5] [G]
 
*Rationale: Having order_id as a nullable field from day one means linking visits to orders in v2 is a one-line application change. Without it, v2 requires an ALTER TABLE migration on a live production database containing months of visit records — a risky and avoidable operation.*
 
**REQ-102: **The backend API shall be structured so that the following v2 endpoints can be added without modifying any existing v1 endpoint: POST /orders, GET /orders, GET /orders/pending, PATCH /orders/:id/assign, PATCH /orders/:id/cancel, GET /riders/:id/orders.    [BRD §G5] [G]
 
*Rationale: These endpoints slot naturally into the existing API structure. Documenting them now ensures v1 API design decisions do not inadvertently block them.*
 
**REQ-103: **The outlet records imported in v1 shall include all fields required by the v2 order intake system: outlet name, owner contact details, and GPS coordinates. No outlet record shall need to be restructured to support order intake.    [BRD §G5, §BRD §4] [G]

# **12. Out of Scope for Version 1**
 
The following are explicitly excluded from v1 and must not be implemented without a formal scope change approved in writing:
 
- Rider self-registration or account modification
 
- Continuous GPS tracking between outlets
 
- Automated performance scoring or penalties based on visit data
 
- Riders having any ability to change outlet status
 
- Automated reactivation of inactive or pullout outlets
 
- Turn-by-turn in-app navigation
 
- Automatic route optimization (deferred to v2)
 
- iOS version of the rider app
 
- Customer-facing features — outlets do not have a login
 
- Payment processing or invoicing
 
- Integration with accounting or inventory systems
 
- Analytics on route deviation patterns (deferred to v2)
 
- Inbound order intake system (deferred to v2)
 
# **13. Acceptance Criteria**
 
Version 1 is accepted when all of the following scenarios can be demonstrated in a field test environment:
 
### **Scenario A — New rider first day**
 
- A tester with no prior knowledge of the route launches the app for the first time
 
- Completes one-time setup using a manager-provided code
 
- Acknowledges the data collection disclosure
 
- Sees active outlet pins on a map of the service area — only outlets with precise or area pin quality are visible
 
- Taps an outlet to view its photo and last visit information
 
- Navigates to the outlet using an external map app via deep link
 
- The geofence triggers automatically upon arrival
 
- Logs a delivered outcome with units and payment
 
- The visit appears in the manager web dashboard within 30 seconds
 
- Entire scenario completed without asking anyone for directions
 
### **Scenario B — Offline operation**
 
- Rider device is placed in airplane mode after shift-start sync
 
- Rider navigates the map, taps outlets, views detail screens
 
- Rider logs 5 visits of mixed outcomes including delivered and no_stock
 
- Device is reconnected to internet
 
- All 5 visits appear in the manager web dashboard within 30 seconds of reconnect
 
- No visit record is lost
 
### **Scenario C — Account lock**
 
- Manager locks a rider account from the web admin while the rider's app is open
 
- If the device is online: the locked screen appears within 10 seconds
 
- If the device is offline: the locked screen appears the moment it reconnects
 
- After lock: no outlet data remains accessible on the device
 
### **Scenario D — High priority route**
 
- Manager creates a route of at least 10 outlets and assigns it to a rider
 
- Manager flags 2 outlets as high priority
 
- Rider receives a push notification within 60 seconds on an online device
 
- Rider opens the map and sees the 2 flagged outlets with a distinct visual marker
 
- Marker is visible even when notifications are disabled on the device
 
### **Scenario E — Data usage**
 
- A full simulated shift is completed: shift-start sync, 20 outlet visits, 10 photo views
 
- Total mobile data consumed is measured and confirmed to be under 5MB
 
### **Scenario F — Manager operations**
 
- Manager creates a new rider account in under 2 minutes
 
- Manager creates and assigns a route of 80 outlets in under 5 minutes
 
- Manager identifies all active outlets not visited in 7 or more days in under 30 seconds
 
- Manager approves a pending rider-submitted photo
 
- Manager filters outlets by location_pin_quality = missing to view the geocoding work queue
 
- Manager changes an outlet status from active to pullout — outlet disappears from rider map immediately at next sync
