# **1. Purpose of This Document**
 
This Implementation Plan translates the requirements documented in ZeroThree BRD v2.1 and SRS v1.3 into a concrete, sequenced build schedule. It defines five phases of development, the specific tasks within each phase, the technologies to be learned and applied, the acceptance criteria that mark each phase complete, and the overall timeline across one semester of approximately 16 to 18 weeks.
 
This document is the working reference for the developer during the build. It is not a fixed contract — decisions made during development may require updates to this plan. All significant deviations should be recorded in the Development Diary with a date and rationale.
 
**Important: **Any feature not listed in the SRS v1.3 scope section is out of scope for v1 and must not be built without a formal decision recorded in the Development Diary.
 
# **2. System Summary**
 
ZeroThree is a three-component field operations system for a San Juan City LPG distribution branch. The three components are built and deployed together but developed in sequence.
 
| **Component** | **Technology** | **Primary purpose** |
| --- | --- | --- |
| PostgreSQL + PostGIS | Node.js + Express | Flutter (Android) |
| Database | Backend API | Rider mobile app |
| Hosted on Supabase. Stores all outlet, rider, visit, and route data with full spatial query support. PostGIS pre-installed. | Connects all components. Handles authentication, geofence logic, sync, push notifications | Primary rider-facing surface. Offline-first. GPS polling, map display, visit logging |
 
| **Component** | **Technology** | **Primary purpose** |
| --- | --- | --- |
| React + Leaflet.js | Cloudinary | Firebase Cloud Messaging |
| Web admin panel | Photo storage | Push notifications |
| Manager-facing browser interface. Outlet management, rider accounts, dashboard, route creation | Free-tier image hosting. Auto-compresses outlet photos to ~200KB on upload | Free Google service delivering push notifications to rider Android devices |
 
**Note: ***Supabase is used as the primary database host throughout all phases including production. It provides PostgreSQL with PostGIS pre-installed, a web-based SQL editor, and a connection string compatible with standard PostgreSQL clients including the Node.js pg library. The Supabase JavaScript client (supabase-js) is not used — all database access goes through the Node.js backend using raw SQL via the pg library. This avoids vendor lock-in at the application layer.*

# **6. Phase 1 — Database**
 
Phase 1 designs and populates the full database schema on Supabase. Every other component depends on this schema being correct. Changes to the schema after Phase 2 begins become progressively more expensive. Get this right before writing any API or app code.
 
**Important: **Do not begin Phase 2 until the nearby outlets query returns correct results from real outlet data. A schema error discovered in Phase 4 is ten times more expensive to fix than one discovered in Phase 1.
 
**Note: ***All SQL in this phase is run in the Supabase SQL editor. There is no need to install PostgreSQL locally — Supabase provides the database and a browser-based query interface.*
 
## **6.1 Database schema**
 
The following tables must be created in this order. Foreign key constraints require parent tables to exist before child tables. Run each CREATE TABLE block separately in the Supabase SQL editor and confirm it succeeds before moving to the next.
 
### **6.1.1 system_config**
 
Stores configurable system parameters. Allows geofence radius and GPS poll interval to be changed without redeploying the app, as required by REQ-072 and REQ-073.
 
| **Column** | **Type** | **Constraints** | **Description** |
| --- | --- | --- | --- |
| key | VARCHAR(100) | PRIMARY KEY | Parameter name e.g. geofence_radius_meters |
| value | TEXT | NOT NULL | Parameter value stored as text, cast in application |
| updated_at | TIMESTAMP | DEFAULT NOW() | Last time this parameter was changed |
 
Seed with: INSERT INTO system_config VALUES ('geofence_radius_meters', '20', NOW()), ('gps_poll_interval_seconds', '10', NOW());
 
### **6.1.2 managers**

| --- | --- | --- | --- |

| email | TEXT | UNIQUE NOT NULL | Login email address |
| password_hash | TEXT | NOT NULL | bcrypt hash — never store plaintext passwords |

### **6.1.3 outlets**
 
Core outlet table. The location column uses PostGIS GEOGRAPHY type for accurate distance calculations on a spherical Earth. Two data quality fields are included per REQ-104 and REQ-105 with check constraints enforcing valid vocabularies.
 
| **Column** | **Type** | **Constraints** | **Description** |
| --- | --- | --- | --- |
| id | SERIAL | PRIMARY KEY | Auto-incrementing outlet ID |
| outlet_name | TEXT | NOT NULL | Store name e.g. Aling Rosa Store |
| outlet_formaladdress | TEXT |  | Full formatted address |
| outlet_city | TEXT |  | City e.g. San Juan City |
| outlet_district | TEXT |  | District within the city |
| outlet_barangay | TEXT |  | Barangay name |
| outlet_area | TEXT |  | Area code or zone label |
| owner_name | TEXT |  | Owner name for rider reference |
| owner_contact | TEXT |  | Owner phone number — required for v2 order intake |
| location | GEOGRAPHY(POINT,4326) | NULLABLE | GPS coordinates. Nullable — not all outlets have verified coordinates yet |
| outlet_status | TEXT | DEFAULT 'inactive' CHECK (outlet_status IN ('active','inactive','pullout')) | active, inactive, or pullout |
| location_pin_quality | TEXT | DEFAULT 'missing' CHECK (location_pin_quality IN ('precise','area','cluster','mismatch','missing')) | Coordinate reliability — see BRD §7a.1 |
| location_verification_level | TEXT | DEFAULT 'unverified' CHECK (location_verification_level IN ('auditor','rider','staff','unverified')) | Who can confirm this outlet — see BRD §7a.2 |
| show_last_visitor | BOOLEAN | DEFAULT FALSE | Controls REQ-010 visibility per outlet |
| show_last_visit_time | BOOLEAN | DEFAULT FALSE | Controls REQ-011 visibility per outlet |
| outlet_concerningbranch | TEXT |  | Which branch services this outlet |
| outlet_last_visit_time | TIMESTAMP | NULLABLE | Denormalized last visit time for fast lookups |
| created_at | TIMESTAMP | DEFAULT NOW() | When record was added |
| updated_at | TIMESTAMP | DEFAULT NOW() | Last update — use a trigger to auto-update |
 
**Note: ***Create a spatial index after import: CREATE INDEX outlets_location_idx ON outlets USING GIST(location); — this makes nearby queries fast. The index handles NULL values gracefully and does not need to be rebuilt when coordinates are added to previously null records.*

### **6.1.6 visits**
 
The most important table in the system. Every outlet interaction by every rider is a row here. The nullable order_id field is included from day one per REQ-101 to support v2 order intake without a schema migration.
 
| **Column** | **Type** | **Constraints** | **Description** |
| --- | --- | --- | --- |
| id | UUID | PRIMARY KEY DEFAULT gen_random_uuid() | UUID so offline-created records have a globally unique ID |
| rider_id | INTEGER | REFERENCES riders(id) NOT NULL | Which rider made this visit |
| outlet_id | INTEGER | REFERENCES outlets(id) NOT NULL | Which outlet was visited |
| outcome | TEXT | NOT NULL CHECK (outcome IN ('delivered','no_stock','no_stop')) | Visit outcome code |
| arrived_at | TIMESTAMP | NULLABLE | When rider entered geofence |
| departed_at | TIMESTAMP | NULLABLE | When rider exited geofence or closed the visit |
| duration_minutes | INTEGER | NULLABLE | Calculated from arrived_at and departed_at |
| units_refilled | INTEGER | DEFAULT 0 | Canisters refilled at ₱32 per unit |
| units_sold_new | INTEGER | DEFAULT 0 | New canisters sold at ₱70 per unit |
| payment_collected | DECIMAL(10,2) | NULLABLE | Combined payment for the visit |
| gps_accuracy_meters | DECIMAL(6,2) | NULLABLE | GPS accuracy reading at geofence entry |
| notes | TEXT | NULLABLE | Optional free-text note from rider |
| order_id | UUID | NULLABLE | Reserved for v2 order intake. Always NULL in v1. |
| created_at | TIMESTAMP | DEFAULT NOW() | When record was inserted — may differ from arrived_at for offline records |
 
**Note: ***Add a check constraint: CONSTRAINT delivered_has_units CHECK (outcome != **'**delivered**'** OR (units_refilled + units_sold_new) **>** 0). This enforces REQ-017a at the database level.*

## **6.2 Key queries to validate**
 
After creating the schema and importing outlet data, verify these queries return correct results before proceeding to Phase 2. Run them in the Supabase SQL editor.
 
| **Query** | **What it tests** | **SRS requirement** |
| --- | --- | --- |
| SELECT name, ST_Distance(location, ST_Point(121.02, 14.60)::GEOGRAPHY) AS dist_m FROM outlets WHERE ST_DWithin(location, ST_Point(121.02, 14.60)::GEOGRAPHY, 2000) AND outlet_status = 'active' AND location_pin_quality IN ('precise','area') AND location IS NOT NULL ORDER BY dist_m; | Nearby outlets query with coordinate quality filter — the most critical spatial query in the system | REQ-001, REQ-002, REQ-107 |
| SELECT o.outlet_name, MAX(v.arrived_at) AS last_visit FROM outlets o LEFT JOIN visits v ON v.outlet_id = o.id WHERE o.outlet_status = 'active' GROUP BY o.id ORDER BY last_visit ASC NULLS FIRST; | Outlets sorted by last visit date — powers route suggestion | REQ-003 |
| SELECT * FROM outlets WHERE outlet_status = 'active' AND id NOT IN (SELECT DISTINCT outlet_id FROM visits WHERE arrived_at > NOW() - INTERVAL '7 days'); | Outlets not visited in 7+ days — powers manager dashboard alert | REQ-052 |
| SELECT location_pin_quality, location_verification_level, COUNT(*) FROM outlets GROUP BY location_pin_quality, location_verification_level ORDER BY location_pin_quality; | Data quality breakdown — manager work queue visibility | REQ-106 |
 
## **6.3 Data import**
 
The outlet spreadsheet has already been partially imported into Supabase during Phase 0 and Phase 1 preparation work. The following steps finalise the import for production use.
 
- Verify all outlet records are present: SELECT COUNT(*) FROM outlets;
 
- Set location_pin_quality per outlet based on coordinate confidence — use the five defined values: precise, area, cluster, mismatch, missing
 
- Set location_verification_level per outlet based on who confirmed the data — use the four defined values: auditor, rider, staff, unverified
 
- Set outlet_status per outlet — active for confirmed active outlets, pullout for outlets where product has been removed, inactive for all uncertain records
 
- Add the spatial index after all coordinates are loaded: CREATE INDEX outlets_location_idx ON outlets USING GIST(location);
 
- Spot-check 20 random outlets by exporting to GeoJSON and viewing on geojson.io to verify pin placement
 
- Run the data quality breakdown query from Section 6.2 to confirm the distribution of quality levels
 
## **6.4 Phase 1 acceptance criteria**
 
- All eight tables created with correct columns, types, constraints, and check constraints
 
- Spatial index exists on outlets.location
 
- system_config seeded with geofence_radius_meters = 20 and gps_poll_interval_seconds = 10
 
- Outlet records imported with status, pin quality, and verification level set per record
 
- Nearby outlets query with quality filter returns correct results for a test coordinate in San Juan City
 
- Nearby query correctly excludes outlets with pin quality of cluster, mismatch, or missing
 
- Last-visited sort query returns outlets in correct order
 
- Check constraint on visits table rejects a delivered outcome with zero units
 
- Check constraint on outlets table rejects invalid outlet_status, location_pin_quality, or location_verification_level values

## **7.3 Security implementation**
 
- All endpoints served over HTTPS — Supabase enforces SSL on the database connection by default. The API host (Railway or Render) provides HTTPS at the platform level.
 
- Manager authentication uses JWT tokens signed with JWT_SECRET from .env. Tokens expire after 24 hours.
 
- Rider authentication uses a long random token stored as a bcrypt hash in riders.auth_token_hash. Invalidated by setting this column to NULL on account lock.
 
- The shift-start sync payload is encrypted with AES-256 using a session key generated per shift. The session key is returned in the sync response and held in Flutter's in-memory state only — never written to device storage.
 
- Passwords and tokens are never logged. Add middleware to strip sensitive fields from request logs.
 
- The Supabase connection string in .env contains database credentials — never commit this file to GitHub.
 
## **7.4 Phase 2 acceptance criteria**
 
- GET /health returns 200 OK
 
- POST /auth/rider/setup returns a token when given a valid setup code
 
- POST /auth/rider/verify returns { status: 'locked' } for a locked account
 
- GET /outlets/nearby returns only active outlets with precise or area pin quality, sorted by distance
 
- GET /outlets/nearby excludes outlets with cluster, mismatch, or missing pin quality even if outlet_status is active
 
- POST /visits with outcome = delivered and both unit fields = 0 returns 400 Bad Request
 
- POST /visits with outcome = delivered and valid units returns 201 Created
 
- PATCH /admin/riders/:id/lock sets auth_token_hash to NULL in the Supabase database
 
- PATCH /admin/routes/:id/outlets/:outletId/priority sends an FCM push notification to the rider's device
 
- GET /sync/shift-start returns a payload under 200KB for the active outlet set
 
- GET /admin/outlets supports filter by location_pin_quality and location_verification_level
 
- All endpoints return 401 Unauthorized when called without a valid token

## **9.3 Offline architecture**
 
The offline system has three distinct layers that must be built in this order:
 
- Layer 1 — Encrypted outlet cache. At shift-start sync, download the active outlet list (precise and area quality only) and assigned route. Encrypt the payload using AES-256 with the session key returned by the server. Store in flutter_secure_storage. Decrypt in memory on demand. Wipe at logout or shift end by deleting the stored key.
 
- Layer 2 — Offline visit queue. When a visit is logged with no internet connection, write it to a local SQLite table (pending_visits) with all fields intact. Include the UUID visit ID generated on the device so it can be submitted to the server without collision.
 
- Layer 3 — Sync on reconnect. The connectivity_plus package fires an event when network connectivity is restored. On this event: call POST /auth/rider/verify to check account status. If active, iterate over pending_visits and POST each to /visits. On success, delete from the local queue. On failure, leave in queue for next reconnect.
 
**Important: **Visit records in the local queue must survive an app crash or phone restart. Use sqflite transactions to ensure records are either fully written or not written at all — never partially written. This satisfies REQ-093.
 
## **9.4 GPS and geofence implementation**
 
- Use the geolocator package to request location permission on first launch
 
- Start a background service using flutter_background_service that polls GPS every 10 seconds (read from system_config at shift start)
 
- On each GPS poll, check the current position against all active outlet locations loaded from the encrypted cache. Calculate distance using the Haversine formula — do not call the API for this.
 
- When a rider enters a geofence (distance <= geofence_radius_meters from system_config): record arrived_at timestamp. Start a 60-second timer.
 
- If the rider is still inside after 60 seconds: trigger the visit logging screen prompt.
 
- If the rider exits before 60 seconds: automatically log a no_stop outcome with no rider input. Record arrived_at and departed_at.
 
- Store gps_accuracy_meters from the geolocator position object with each visit record.
 
- If GPS accuracy is worse than 50 meters at the moment of geofence entry: show the out-of-range warning per REQ-024 but allow the rider to proceed.

# **12. Implementation Risk Register**
 
The following risks are specific to the implementation phase. Business risks are documented in BRD v2.1 Section 17.
 
| **Risk** | **Likelihood** | **Impact** | **Mitigation** |
| --- | --- | --- | --- |
| Background GPS service killed by Android battery optimisation on some phone manufacturers | High | High | Test on Samsung, realme, and Xiaomi devices. Add manufacturer-specific battery optimisation bypass instructions to the app setup guide. Use flutter_background_service which handles this better than raw isolates. |
| Supabase free tier project pauses after 7 days of inactivity | Medium | Low | Active development will prevent pausing. Be aware the project takes ~20 seconds to wake up after inactivity. Upgrade to paid plan if this becomes a problem in production. |
| Supabase SSL requirement causes Node.js pg connection errors | Medium | Medium | Add ?sslmode=require to the connection string or set ssl: { rejectUnauthorized: false } in pg client options. This is a one-line fix but easy to overlook on first connection. |
| Outlet coordinate quality worse than expected — too few precise/area outlets to show riders | High | Medium | Even 50 active outlets with reliable coordinates provide immediate value. Expand the active set incrementally as field verification improves pin quality. |
| Offline sync produces duplicate visit records when the same record is submitted twice | Medium | Medium | Use UUID primary keys generated on the device. The server must implement idempotency — a second POST with the same UUID returns 200 rather than creating a duplicate. |
| MBTiles map tile package is too large | Medium | High | Generate tiles only for zoom levels 13 to 17 (street level). For the 7-area service zone this should be under 150MB. Download tiles over WiFi at first shift-start sync rather than bundling in APK. |
| Phase 4 runs over schedule due to Flutter learning curve | High | Medium | If behind by Week 13, defer photo submission feature. Core features — map, geofence, visit logging, offline sync — must ship. |
| Session key management causes encrypted cache to become unreadable mid-shift | Low | High | Store session key in Flutter's in-memory state only. If the app is killed and restarted mid-shift, prompt the rider to perform a new shift-start sync rather than attempting to recover the previous session. |
